What changed from v1

v1 was, in the reviewers' words, “an outstanding decision document and an incomplete specification.” It settled principles precisely and left every load-bearing quantity undefined. Three things are structurally different here:

  • Every quantity is a number. The request window, the area unit, the dispense unit, the capacity unit, the reliability formula — each has a value, not a description.
  • Every promise has a mechanism. v1 granted access to allergy data no screen collected, gave a safety alert an exit with no surface, and described a pharmacy application flow with zero screens. Each of those is now either built or removed — never asserted.
  • Phase 0 is closed. It contains everything it needs and refers to nothing scheduled later. Where something could not be closed inside Phase 0, it was removed from Phase 0 rather than left dangling.

The single biggest change

The riskiest assumption is now tested first, not last v1 forbade every mechanism that could populate the medication record — no questionnaire, no pharmacist entry, no typed quantity, no dose amount, no pack size, no free text, no edits — each for a good reason, in a different section, and never summed. The record was expected to fill itself.

v3 gives it exactly one automatic source: completed pickups. Phase 0 therefore ships no prediction, no reminders and no supply indicator, and its exit gate measures whether the record actually accretes (D22 D23). If it does not, we learn that in 90 days instead of after four phases built on the belief.

Scope of this document

Architecture only. No implementation, no UI design, no database, no API, no code. Wording, formatting and documentation style are out of scope by instruction; where copy appears it is because the meaning of the string is an architectural decision (what the product is permitted to claim).

Two invariants that hold across the whole model 1. Every clinical read and write names a subject and an acting account separately. They are frequently different people, and collapsing them is how one person's record acquires another person's facts.
2. Nothing clinical is ever edited or deleted. Corrections are new records. There is no role with the permission and no operation that performs it.

3 · Phase 0 Closed System

Rebuilt from zero. Everything Phase 0 needs is inside Phase 0. There are no references forward and no hidden dependencies.

What Phase 0 is

Phase 0 in one sentence Dawai tells a patient which nearby verified pharmacy has the item they need, and asks that pharmacy to physically set it aside — and records what they collected.

It does not dispense, take payment, deliver, give clinical advice, machine-read a prescription, or check interactions. It is deliberately scoped so that the regulatory answer, when it arrives, cannot invalidate the work (D41).

In Phase 0

Capabilities

  • Guest browsing and search, no account required
  • Account by phone + code; managed subjects for people who cannot authenticate
  • Family: peer grants (View, View+Order) and guardianship
  • Nearby pharmacies with open/closed, distance, and hours
  • Multi-line requests, with a prescription image where required
  • Per-line offers, with substitution by a licensed pharmacist
  • Reservations with a code, a clock, and a defined failure path
  • Handover with a recorded checklist
  • Dispense history — the record, built automatically
  • Full pharmacy application, verification and branch operation
  • Notifications, offline queueing, and an outbox
  • Operator console: verification, catalogue, support, audit, and the four exit metrics

Explicitly not in Phase 0

  • Interaction checking, safety alerts, allergy data D16D17
  • Dose schedules, reminders, adherence, supply prediction, the blister strip D22
  • Stock movements, spot counts, SKU trust
  • Payments, delivery, chat, ratings, promotions D31
  • Machine-read prescriptions
  • Controlled substances D42
  • Kurdish and English D34
  • Wallet passes, live activities, biometrics, widgets, voice D35
  • Broadcasts, bulk export, role granting, two-person controls D20
  • Price visible anywhere outside an offer D08

Prerequisites — must exist before the first request

  1. One launch district named in configuration D40
  2. The district list curated for that city D10
  3. A catalogue where every requestable item has a pack size, a prescription flag and a controlled flag D07 D18 D42
  4. An operator account able to verify pharmacies D20

Four enforcement rules

  1. Hidden UI is not a permission. The client enforces nothing.
  2. Authority is checked where the work happens, not at the entry point — entry-point checks get bypassed the first time an internal caller is added.
  3. A missing relationship is indistinguishable from a forbidden one. Confirming that a record exists but is forbidden turns any lookup into an identity oracle.
  4. Least privilege wins on ambiguity. Where several grants could apply, the narrowest is used — never the first found and never the widest.

7 · Clinical Safety

The minimum safe Phase 0. No fake safety, no fake clear, no implied clinical certainty, and every rule has a named owner.

Phase 0's clinical position, stated exactly Dawai performs no automated clinical checking of any kind in Phase 0. It says so in the product, on the request confirmation screen and on every medicine page: «دوائي ما يفحص تعارض الأدوية. اسأل الصيدلي.»

This is deliberate. A partial check the user believes is complete is more dangerous than a stated absence — and v1's check existed only on the reorder path, so every newly added medicine bypassed it while the interface implied coverage.

8 · Marketplace Logic

Availability, reservation, holds, partial requests, price disputes, reliability and cold start — redesigned, with the core vision unchanged.

Availability

Dawai holds no stock data in Phase 0. Availability is not a stored fact; it is a question asked of real pharmacies in real time. This removes the entire class of "our data says they have it and they do not".

  • A medicine page shows observed availability: how many nearby branches answered available for this item in the last 7 days. Never a stock figure.
  • A branch may mark an item not carried, which stops it receiving those requests and is the only inventory-shaped data Phase 0 keeps.
  • Decline reasons are the highest-quality signal collected, which is why declining costs one tap.

Routing — who receives a request

A branch receives a request if all five hold. There is no ranking, no weighting, and no paid placement — every eligible branch is asked simultaneously D12.

  1. Verified, with a licence that has not lapsed
  2. The subject's district is inside the branch's declared coverage
  3. Open now, or opening within the request's window — in which case the notification is deferred to opening time D09
  4. Not paused, and below its declared capacity
  5. Has not marked any requested item "not carried"
Request windows now = 20 minutes · today = 4 hours · خلال يومين = 48 hours. One rule, replacing v1's three contradictory statements about closed pharmacies.

One reservation = one branch = one code = one clock. A patient may hold two reservations from one prescription; Today groups them D06.

Offer, hold, and the distinction the product rests on

An offer

  • Commits nothing
  • Can be withdrawn until accepted
  • No clock
  • Any staff member may send one
  • Says so on screen: «إرسال العرض ما يحجز شي»

A reservation

  • Commits physical stock
  • Cannot be withdrawn — only failed, with a reason
  • The clock starts here, never earlier
  • Any staff member may confirm — it is a commercial act D19
  • Failing it counts, unless reported within 5 minutes

Price

  • The offer price is binding from acceptance until the reservation ends, and the compose screen says so before sending.
  • The correction path is withdrawal before acceptance, not a later adjustment D08.
  • A difference at the counter is reported by the patient, recorded against the branch, and visible to the operator. There is no refund because there is no payment.
  • No price appears anywhere outside an offer made to a specific patient. Not on the medicine page, not in search, not in any comparison view.

Reliability

One number, one formula, no decimals shown honoured = collected ÷ (collected + failed-after-confirmation) over 60 days, hidden below 10 reservations. A failure reported within 5 minutes of confirming does not count — that is the honest "sold since" case. Patients see a band only: موثوقة · جديدة · تحتاج انتباه. A decimal invites an argument about a number instead of about the behaviour D11.

Cold start

Density before geography, enforced architecturally rather than as an intention:

  • One launch district, named in configuration before the first pharmacy is verified D40
  • Requests outside it are refused with an honest message and a waitlist — never zero results
  • The operator's coverage screen is a launch instrument, present in Phase 0 rather than two phases later
  • Unmatched searches are the recruitment list: what people asked for and did not get, by district

The trade-off, stated openly A guardian holds unilateral authority over another person's health record with no consent step — because there is nobody able to consent. That is a real coercion risk and we accept it, because the alternative is a product that cannot serve the person it was built for. Four controls bound it: exactly one guardian (so there is never a conflict to resolve), every guardian action attributed and visible to the subject on claim, notification to all grant holders on memorialisation, and platform-side reversal on dispute.

Identity recovery and number churn

SituationResolution
User changes number, still holds the old oneIn-app change with verification of both. Grants survive; sessions do not.
User lost the number entirelySupport path. Proof is the reservation history — items, branches, dates — which only the account holder knows.
Number reassigned to a strangerA new sign-in on a number with an existing account triggers re-verification and a security hold. The prior record is never exposed.
Guardian loses their phoneRecovering the account recovers every dependent with it, since they have no separate credential.
Guardian becomes unreachablePlatform-mediated guardianship transfer on request, logged, with notice to the current guardian.

Deletion and its blast radius

  • Deleting an account forces an explicit per-dependent choice: transfer to another account, or delete. There is no default D05.
  • Deleted: account, self-subject, chosen dependents, dispense history, prescription images, saved pharmacies, unmatched-search records.
  • Retained: the branch's own reservation records, pseudonymised — code, item, date, price, with no name and no link back — for 3 years; and audit entries with the actor replaced by a tombstone.
  • The deletion screen states exactly this, because stating it is that screen's entire purpose.

What the pass changed

  1. Confirm scope removed from peer grants. v1 had View < Order < Confirm. With no dose events in Phase 0, Confirm governs nothing — an implied permission over a capability that does not exist.
  2. Branch pause split by role. A temporary same-day pause is an operational act any staff member needs at the counter; changing declared capacity is configuration and is manager-only.
  3. A queued-actions screen added on both sides. The offline rule required a surface that did not exist, and a pharmacy answering offline needs it as much as a patient.
  4. Eligibility panel added. Routing filters were invisible to the branch they filtered.
  5. The last manager cannot be removed. Otherwise a branch reaches a state with no one able to configure it.
  6. Observed availability replaced stock display. With no stock data in Phase 0, any availability figure had no source.
