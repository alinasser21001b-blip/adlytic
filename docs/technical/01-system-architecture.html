Clients

Patient App §3 Phase 0 · §4 groups Entry/Subjects/Find/Request/Reservation/Account
Responsibilities
  • Render patient screens E1–E13, S1–S12, F1–F8, R1–R13, V1–V8, M1–M15
  • Hold the encrypted local cache while signed in (D28)
  • Own the outbox: queue writes offline, replay exactly once (D27)
  • Preserve a pending action across authentication (D26)
Must never
  • Decide any permission — hidden UI is not a permission (§5 rule 1)
  • Show a price outside an offer made to this patient (D08)
  • Present a queued request as sent (D27)
  • Assert a clinical fact the server has not accepted
  • Contain any pharmacy or operator screen (role isolation, §5)
Pharmacy App §4 groups Pharmacy apply/Pharmacy
Responsibilities
  • Render PA1–PA9 and P1–P31
  • Staff session with per-person PIN and 30-minute idle timeout (D19)
  • Own its outbox for offline answers (P31)
Must never
  • Read any clinical record (§5 clinical matrix)
  • See requester identity before acceptance (§5 marketplace matrix)
  • Retain a prescription image after its reservation ends (D18)
  • Contain any patient or operator screen
Owner Console §4 group Operator (O1–O24)
Responsibilities
  • Render O1–O24
  • Present the four Phase 0 exit metrics (§3)
Must never
  • Write into a clinical record — no mechanism exists (§5 platform matrix)
  • Read identified clinical data outside a consented session (D-support, O19)
  • Modify the audit log
  • Broadcast, bulk-export or grant roles — absent in Phase 0 (D20)

Edge and services

API Gateway api-gateway §5 enforcement rules 1–4
Responsibilities
  • Terminate TLS, authenticate the caller, resolve the principal
  • Reject a token whose audience does not match the endpoint's persona (role isolation)
  • Enforce idempotency keys on every state-changing call (D27)
  • Rate limit per account and per branch (§8 abuse table)
  • Emit an audit envelope for every request that touches identified data
Depends on
identity-service · audit-service
Must never
  • Contain business logic of any kind
  • Perform the authority check itself — authority is checked where the work happens (§5 rule 2)
  • Cache a clinical response
Identity Service identity-service §9 Family Architecture · §2 Account/Subject/Grant · §6 Subject & Grant machines
Responsibilities
  • Accounts, phone verification, sessions, device binding
  • Subjects: self and managed; the claim transition; memorialisation
  • Guardianship: creation, transfer, ending on claim
  • Peer grants: invite, pending, approve, narrow, revoke, expire
  • Answer the single authority question: may principal P act on subject S at scope X
  • Account deletion with per-dependent disposition (D05)
Depends on
audit-service
Must never
  • Store any clinical content
  • Return a boolean for authority — it throws, so a caller cannot forget to handle it (§5 rule 2)
  • Distinguish a missing relationship from a forbidden one in its error (§5 rule 3)
Marketplace Engine marketplace-engine §8 Marketplace Logic · §6 Request/Offer/Reservation machines
Responsibilities
  • Requests and their lines; the child-request rule for unfilled lines (D06)
  • Routing: the five eligibility rules, evaluated per branch (§8)
  • Request windows: 20m / 4h / 48h, and deferred notification to opening time (D09)
  • Offers and their lines; withdrawal before acceptance (D08)
  • Reservations: confirm, refuse, expire, cancel, collect — server-authoritative clock
  • Honoured rate with the 5-minute grace, banded, never a decimal (D11)
  • Observed availability from answers, never from stock (§8)
Depends on
identity-service · catalogue-service · pharmacy-service · clinical-engine · audit-service
Must never
  • Hold stock quantities — Phase 0 has no stock data (§3)
  • Rank or weight branches; every eligible branch is asked simultaneously (D12)
  • Expose requester identity in any branch-facing projection (§5)
  • Start a reservation clock before the branch confirms (§6 Reservation)
  • Decide whether a substitution is clinically acceptable — that is clinical-engine
Clinical Engine clinical-engine §7 Clinical Safety
Responsibilities
  • Enforce the prescription gate: a POM line cannot exist without an image (D18)
  • Refuse controlled items outright (D42)
  • Authorise a substitution proposal — verified pharmacist licence only (D19)
  • Define and record the handover checklist (§7 control 2)
  • Write the dispense record on collection — the only writer of the medication record (D22)
  • Own the refusal list: no diagnosis, no dose, no auto-substitution, no OCR, no allergy data (§7)
Depends on
catalogue-service · pharmacy-service · identity-service · audit-service
Must never
  • Perform any interaction check — Phase 0 has none (D16)
  • Hold or read allergy data — it does not exist in Phase 0 (D17)
  • Machine-read a prescription (§7 refusals)
  • Ever return a clear result; in Phase 0 it returns only ALLOWED or REFUSED, never SAFE
  • Edit or delete a dispense record (§2 invariant 2)
Catalogue Service catalogue-service §2 CATALOGUE_ITEM/DISTRICT · §8 availability · O8–O11
Responsibilities
  • Catalogue items with pack size, prescription flag, controlled flag (D07/D18/D42)
  • Arabic-first search with orthographic normalisation, never silent correction
  • The curated district list (D10)
  • Unmatched searches — the only search data retained (D29)
  • Observed availability windows computed from offer answers
Depends on
audit-service
Must never
  • Hold a price (D08)
  • Hold stock
  • Autocorrect a medicine name silently (§9 of v1, carried into D-search)
  • Publish an item lacking pack size, prescription flag or controlled flag (§3 prerequisite 3)
Pharmacy Service pharmacy-service §4 Pharmacy apply/Pharmacy · §6 Verification & Branch eligibility machines
Responsibilities
  • Pharmacies, branches, verified map points, staff and roles
  • Verification lifecycle, licence expiry tracking with 60/30/7-day warnings
  • Opening hours, exceptions, the Ramadan alternative week (D33)
  • Coverage, capacity, pause; computing branch eligibility and its reason (D13)
  • Branch data rights: access log, export, closure (D15)
Depends on
identity-service · audit-service
Must never
  • Decide routing — it answers eligibility, marketplace-engine routes (§8)
  • Hold clinical data
  • Allow the last manager of a branch to be removed (§10 change 5)
Notification Service notification-service §4 E10/M6 · D30 watches · D09 deferred notification
Responsibilities
  • Device registration, per-category preferences, quiet hours
  • Deliver push for the Phase 0 categories only
  • Defer a branch notification to its opening time when the request window allows (D09)
  • Watch matching and expiry at 14 days, max 5 per subject (D30)
Depends on
identity-service
Must never
  • Compute clinical severity — Phase 0 has none, and it would eventually disagree with clinical-engine (§7)
  • Notify a branch outside its opening hours except for a reservation it already confirmed (D09)
  • Send anything for engagement
  • Contain a category that cannot be disabled — Phase 0 has no safety category (M6)
Media Service media-service §2 PRESCRIPTION_IMAGE · D18 · P15
Responsibilities
  • Prescription image storage, encrypted at rest
  • Time-bounded access grants: readable by a branch only while its reservation is live
  • Revocation when the reservation ends
  • Deletion on patient request or account deletion
Depends on
identity-service · audit-service
Must never
  • Machine-read an image (§7 refusals)
  • Serve an image after its reservation ends (D18)
  • Store an image outside the patient's ownership (§9 deletion)
Audit Service audit-service §2 AUDIT_ENTRY · §5 platform matrix · S12/P26/O23
Responsibilities
  • Append-only record of every action and every read of identified data
  • Project the patient-facing access log (S12) and the branch access log (P26)
  • Serve the operator audit log and entry detail (O23/O24)
  • Tombstone the actor on account deletion rather than removing the entry (D05)
Depends on
nothing
Must never
  • Offer an update or delete operation to any principal, including the operator (§5)
  • Drop an entry under load — it applies backpressure instead
  • Store the content of a clinical record; it stores that a read occurred, not what was read

The rule this architecture is built on No component introduces business logic. Every behaviour here exists because Blueprint v3 specifies it, and every element carries the reference. Where the Blueprint does not specify something the implementation needs, it is recorded as a gap in the validation report — never invented.
