# 03 — Action authority audit

## permitAction is a veto, not a validator

```ts
if (!actionCode) return { allowed: true };
if (reconciled.forbiddenActions.includes(actionCode)) return { allowed: false, reason };
return { allowed: true };
```

A membership test against `forbiddenActions`, which `reconcileIntelligence()`
fills **only** from `CREATIVE_ACTIONS` and `AUDIENCE_ACTIONS`. For any code
outside that union it returns `allowed: true` unconditionally — it would
return `allowed: true` for the string `"BANANA"`. That is the absence of
jurisdiction, not a clearance.

```
PERMIT_ACTION_DOMAIN = REFRESH_CREATIVE, REFRESH_CREATIVES, CHANGE_CREATIVE,
                       NEW_CREATIVE, IMPROVE_HOOKS, EXPAND_AUDIENCE,
                       WIDEN_TARGETING, INCREASE_BUDGET, DECREASE_BUDGET,
                       BROADEN_AUDIENCE, CHECK_TARGETING,
                       REVIEW_BUDGET_PACING, NARROW_AUDIENCE
PERMIT_ACTION_DOMAIN_COUNT = 13
DECISION_ENGINE_DOMAIN     = SCALE_BUDGET, HOLD_AND_MONITOR, REFRESH_CREATIVE,
                             PAUSE_CAMPAIGN, KEEP_COLLECTING, RESCUE_WATCH,
                             EMERGENCY_PAUSE
DECISION_ENGINE_DOMAIN_COUNT = 7
DOMAIN_OVERLAP = { REFRESH_CREATIVE }   — exactly one, and load-bearing
```

The overlap is the code behind the cmoFeedV2 authority gap. The domains are
**separated, not disjoint**; a test pins that `REFRESH_CREATIVE` stays
FORBIDDEN under POST_CLICK.

No cell exists where the recommender emits an action the guard forbids for
that class: `templateFor` returns `FIX_*` codes for POST_CLICK/CONVERSION and
`REFRESH_CREATIVE` only for CLICK, so its output is already aligned with the
veto by construction.

```
RECOMMEND_GUARD_REAL_GAP = YES — vacuous for 4 of 6 templates
UNGOVERNED_RECOMMENDATION_ACTIONS = FIX_MESSAGING_DESTINATION, FIX_LANDING_PAGE,
                                    FIX_CONVERSION_STEP, REVIEW_BIDDING
FIX_REQUIRED = NO — permitAction is NOT widened
```

Widening the veto to cover them would be a new semantic claim about which
problem classes contradict which fixes, and that claim is not derivable from
the funnel today. The Observatory instead reports
`authorityRelation: NOT_GOVERNED` whenever the recommended action is one of
these, so the gap is visible rather than papered over.

## DTO authority labelling — fixed

`applyCmoFeedAuthorityGuard` stamped `permitted: true` on codes drawn from
`insightType`, which is the **DecisionEngine** vocabulary. Behaviour was always
correct — nothing that should drop was kept — but the label asserted a check
that structurally could not run.

`CmoFeedItemDTO.authorityRelation` now carries `GOVERNED` / `NOT_GOVERNED`
beside `permitted`. No filtering changed.
