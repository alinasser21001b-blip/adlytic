UPLOAD STEPS (every time)
  1. Cancel ALL Queued/Building on thriving-manifestation + lively-insight
  2. Confirm those two have Auto Deploy DISABLED
  3. Confirm adlytic Config File Path = /railway.json
  4. Push to main  OR  adlytic → Cmd+K → Deploy Latest Commit
  5. Wait until adlytic shows ACTIVE (one service only, ~5–8 min)
  6. Verify:
       curl https://adlytic-production.up.railway.app/api/health
       curl -sL .../login | grep -c 'function escHtml'   # must be >= 1
       Hard refresh /recommendations and /settings

  https://railway.app/account/tokens  → create "No Team" token
  GitHub repo → Settings → Secrets → RAILWAY_TOKEN
  Then Actions workflow deploys ONLY adlytic via API.

═══════════════════════════════════════════════════════════════
  TEMPORARY: Brain Observatory validation service (read-only)
═══════════════════════════════════════════════════════════════
Purpose: let an admin open /admin/brain-observatory against REAL synced
Meta data on a feature branch, WITHOUT touching the adlytic production
service or its auto-deploy, and WITHOUT running any background writer.

  1. Railway UI → this project (69ca3009-3a67-4d92-b808-6e4f278335d6)
     → New → GitHub Repo → same repo → branch
     claude/adlytic-graphify-analysis-ai34bu (NOT main).
  2. Name the service e.g. "adlytic-brain-validation".
  3. Settings → Config File Path = /railway.validation.json
     SET THIS BEFORE THE FIRST DEPLOY. Its startCommand omits
     "prisma migrate deploy" on purpose — this service must never run
     migrations; only the primary "adlytic" service does that.
  3b. Settings → Start Command = node dist/src/api/serve.js
     Belt and braces: nixpacks.toml's [start] cmd IS
     "npx prisma migrate deploy && node dist/src/api/serve.js", and the
     config file's startCommand is what overrides it. Setting it in the
     UI too means a mis-set Config File Path cannot silently fall back
     to the migrate-prefixed command.
     (Safety net if it ever did: this branch adds ZERO migrations vs
     main — 39 files on both sides, byte-identical — so a stray
     "migrate deploy" is a no-op, not a schema change.)
  4. Settings → Deploy → Auto Deploy = OFF (railway.validation.json's
     watchPatterns already point at a path that never matches, same
     trick as thriving-manifestation/lively-insight above — deploy
     only ever happens when YOU trigger it manually).
  5. Variables → do NOT type any secret. Use Railway's own reference
     syntax so nothing is ever copy-pasted:
       DATABASE_URL              = ${{Postgres.DATABASE_URL}}
       JWT_SECRET                = ${{adlytic.JWT_SECRET}}
       TOKEN_ENCRYPTION_KEY       = ${{adlytic.TOKEN_ENCRYPTION_KEY}}
       PLATFORM_ADMIN_EMAILS     = ${{adlytic.PLATFORM_ADMIN_EMAILS}}
       ALLOWED_ORIGINS           = ${{adlytic.ALLOWED_ORIGINS}}
       NODE_ENV                  = production
       META_APP_ID / META_APP_SECRET / META_REDIRECT_URI / etc.
                                  = ${{adlytic.<same name>}} (only if a
                                    route needs them to boot; the
                                    Observatory itself needs none of
                                    these — see src/config.ts)
     WHY THOSE FIVE AND NOT FEWER: with NODE_ENV=production,
     src/config.ts's validateRequired() makes JWT_SECRET (>=32 chars),
     TOKEN_ENCRYPTION_KEY and DATABASE_URL fatal at boot (process.exit(1)),
     and an empty ALLOWED_ORIGINS is separately fatal (config.ts's
     production branch). PLATFORM_ADMIN_EMAILS is not boot-fatal but the
     admin guard is fail-closed — every /api/admin/* route answers 503
     without it, so the Observatory would be unreachable.
     Then ADD (new on this service only — do not set these on adlytic):
       SERVICE_ROLE               = api
       SKIP_STARTUP_SYNC_CLEANUP  = true
       BULLMQ_ENABLED             = false
     SERVICE_ROLE MUST BE EXACTLY "api". It FAILS OPEN: config.ts accepts
     only 'api' or 'worker' and silently falls back to 'combined' for
     anything else — and 'combined' STARTS the sync loop, BullMQ workers,
     the onboarding loop and daily maintenance. The dangerous state is the
     default. The booleans accept 1|true|yes|on (case-insensitive).
  6. Deploy. Wait for ACTIVE, then:
       curl https://<this-service>.up.railway.app/api/health
     Confirm in the deploy log — these four lines are the proof that no
     background writer started, and that no migration ran:
       "SERVICE_ROLE=api — background sync/queues run in the worker service"
       "SKIP_STARTUP_SYNC_CLEANUP=true — startup orphaned-SyncJob sweep skipped"
       "[adlytic:queue] BULLMQ_ENABLED=false — workers not started"
       and NO "prisma migrate deploy" anywhere in the log.
     Then log in at https://<this-service>.up.railway.app/login with a
     PLATFORM_ADMIN_EMAILS account and open /admin/brain-observatory.
     (The session cookie is host-scoped — Path=/; HttpOnly; SameSite=Lax
     with no Domain attribute — so logging in on this new hostname works
     independently of the production domain's session.)
     If the log shows a CORS/ALLOWED_ORIGINS rejection for this new host,
     append this service's own URL to its ALLOWED_ORIGINS (overriding the
     reference) and redeploy — the host is not knowable until Railway
     assigns it.
  7. Teardown when done: Railway UI → this service → Settings →
     Danger → Delete Service. Nothing else is affected — the
     production "adlytic"/"thriving-manifestation"/"lively-insight"
     services and the shared Postgres are untouched by this service's
     entire lifecycle (it never migrates, never syncs, never writes
     on a schedule — see SKIP_STARTUP_SYNC_CLEANUP / SERVICE_ROLE=api
     in src/config.ts and src/api/serve.ts).

Do NOT paste DATABASE_URL/JWT_SECRET/META_* values into chat, a PR, or
any file in this repo — Railway's ${{Service.VAR}} reference syntax
above copies the value internally without ever displaying it to you.
